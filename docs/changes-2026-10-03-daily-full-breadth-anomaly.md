## 3. 根因

**两个因素叠加**：

1. **日更链路用窗口式增量更新**
   `每日行业报告.command:97`：`build_industry_daily_full.py --days 60`
   而 `build_industry_daily_full.py` 的 upsert 逻辑是：
   ```python
   kept   = prev[~prev[key].isin(daily[key])]   # 窗口外的历史：原样保留
   merged = concat([kept, daily]).drop_duplicates(key, keep="last")
   ```
   ⇒ **窗口外（>60 个交易日前）的历史永远不会被重算**。

2. **上游行情数据当时不完整**
   `market/daily/` 中 **2026-05 ~ 2026-09 的全部文件 mtime 都是 `2026-09-23 22:52`**
   ⇒ 这批行情是在 **09-23** 才被重写/回填的。
   ⇒ 07-01~07-13 期间跑日更时，MA20 取不到足够历史 ⇒ 宽度算不出
   ⇒ 落到 `daily_full` 里就是 **0**（而非 NaN）。

3. **坏值固化**：09-23 补全行情后，日更的 60 日窗口已滚过 07-01~07-13
   ⇒ **再也不会被重算**。截至 09-30 的产物仍带着这 9 天坏值。

> ⚠️ **通用教训**：**窗口式 upsert（`--days N`）× 上游数据延迟补齐 = 不可逆的历史坏值。**
> 坏值一旦滚出窗口就永久固化，而现有 `check_data_completeness.py` **只校验"有没有/空不空"，
> 抓不到"有行但值坏"** —— 这正是 C4 要补的能力。

## 5. 修复与防御建议

### 5.1 数据修复（源端，一次性）

```bash
cd ~/quant/industry-radar
python3 scripts/build_industry_daily_full.py --days 2000 --force-overwrite
python3 scripts/regime_classifier.py
python3 scripts/build_nav_924.py
# 台账冷区信号须重算（见 docs/action-items.md A4 的完整序列）
```

`--force-overwrite` 走整表覆盖，会**重算全部 1636 天** ⇒ 覆盖坏值。

### 5.2 防御（**待拍板**，因为会改变日报退出码行为）

给 `scripts/check_data_completeness.py` 增加一条**值域规则**，例如：

- `industry_daily_full` 当日 `breadth` 的**非零行业数 = 0** → `CRITICAL`
- 或：`breadth.mean() == 0` 且该日不是数据起始期（如 `date > 数据首日 + 30 个交易日`）→ `CRITICAL`

> ⚠️ 该规则会**参与退出码**（现有 WARNING 即如此），可能让日报在健康日也报错 ⇒ 须先定阈值口径。

### 5.3 治本（**待拍板**）

`--days 60` 的窗口与"窗口外永不重算"的组合是根因之一。候选：

| 方案 | 代价 |
|---|---|
| 改 `--days 2000`（每日全量重算） | 慢（本次沙箱全量重算约 27 秒；源端更快） |
| 保留 60，但**加大到覆盖 MA20 成型期 + 安全边际** | 治标：仍无法覆盖"历史被补数"的场景 |
| 引入**数据版本探测**：行情文件 mtime 变化 → 自动触发该段重算 | 复杂，但真正治本 |
