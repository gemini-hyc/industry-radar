
## 为什么分两层

本机 `~/quant-data` 是**只读副本**，会随源端日更而变化。这一条事实决定了测试必须分两层 ——
否则测试要么天天误报红、要么形同虚设：

| 层 | 文件 | 判据 | 失败意味着 | 进入退出码 |
|---|---|---|---|---|
| **① 结构不变量** | `test_invariants.py` | 由**代码**决定、不该随数据增长而变 | 有**真问题**（schema 漂移 / 键重复 / 口径分裂） | ✅ 是 |
| **② 数值快照** | `snapshot.py` | 由**数据**决定、随源端同步而变 | **供人判断**（数据变化 还是 行为回归） | ❌ 否 |

**核心分寸**：把数值快照写成硬断言，源端每多跑一天日更测试就红一次 ——
那种红没有信息量，只会训练人忽略测试。反过来把结构不变量写成软报告，
真正的 schema 漂移就会被放过。

### ① 结构不变量（19 项）

| 检查 | 抓什么 |
|---|---|
| 产物存在 / 列集合精确匹配 | **schema 漂移** —— 列增删会让下游静默失败 |
| 唯一键无重复 | 键重复会**静默放大**下游统计，最隐蔽的一类脏数据 |
| 完整网格（`131 × 1636 = 214,316`） | **缺格** —— 漏算不报错，只少行 |
| PIT 成员表**刻意不满格**（反向断言） | 防有人把它改回静态成分（D8/D10） |
| 行业集合各处一致（131） | **口径分裂** —— 各产物用了不同的行业域 |
| 日期单调递增 + 跨产物子集关系 | **日期回跳 / 时序错位**（下游跑在主面板之前） |
| 值域（`breadth∈[0,1]`、`up_pct∈[0,100]`） | 口径或计算错误 |
| 关键列零 NaN + 宽度未整体退化 | 上游断链；`breadth` 大面积 NaN = P0-2 那类事故 |
| `regime` 类别 ⊆ 合法集合 | 陌生类名（真 bug）；**容忍**副本待重算的 5 类 |
| 台账 `source` ⊆ 已登记来源 | 绕过 `SOURCE_SPECS` 登记就写台账（违反铁律③） |

### ② 数值快照

记录每个产物的行数 / 日期范围 / 天数 / 行业数 / 关键统计量，与基线对比后**分类**：

```
⬆️ INFO   数据增长（行数增加**且日期右端推进**）—— 正常
⚠️ WARN   需关注：行数减少 / 行数增加但**日期未推进**（重复写入？）/ 行业数变动 / 统计量剧变
```

> 💡 「行数增加」**不能**无条件判为正常：数据没更新却多算了行，是重复写入或去重失效的典型征兆。
> 所以判据结合了「日期右端是否推进」。

更新基线（**会把当前状态固化为新锚点，请连同 change doc 一起提交**）：

```bash
make snapshot          # 等价于 python tests/snapshot.py --update
```

## 与 `tools/dev_verify.sh` 的分工

两者**互补，不能互相替代**：

| 工具 | 回答的问题 | 输入 |
|---|---|---|
| `tools/dev_verify.sh <脚本>` | 「我这次的**改动**，产物 diff 是什么」 | **同一份数据**，**两份代码**（`git archive HEAD` vs 工作树） |
| `tests/run_tests.py` | 「当前产物**结构**是否健康」 | **一套代码**，**单一时刻** |

典型用法是**串联**：先用 `dev_verify.sh` 确认改动没改坏产物，再用本套件确认产物结构仍然合法。

## 已知缺陷的「条件化断言」

`test_invariants.py:TestKnownDefects` 是一个值得注意的设计。

`scripts/regime_classifier.py:50` 明确记载：

> `【已知缺陷，暂不改】calc_top5_conc 在上涨行业不足 5 个时会返回负值`

如果直接断言 `top5_conc ∈ [0,1]`，测试**从第一天起就红**，久而久之没人再看它 —— 这是测试套件最常见的死法。
所以改为**条件化**：负值本身允许（已知行为），但**若负值出现在普涨日**（`up_pct > 5%`），说明计算逻辑回归，必须红。

> 教训：**值域约束不能凭语义猜，必须查代码里的已知行为。** （写这套件时我先是把
> `top5_conc` 断言成 `[0,1]`，跑起来才发现有 10 个负值，回头翻代码才看到那行注释。）

## `selftest.py` —— 测试的测试

```bash
make selftest          # 等价于 python tests/selftest.py
```

一个回归套件最大的失败模式不是「有 bug 没抓到」，而是**它其实永远绿**：断言拿错对象、
异常被吞、目录指错、退出码恒 0。`selftest.py` 用**受控注入**证明每条断言都具备抓取能力：

- **① 11 例结构破坏** → 每个都应让**特定的那个测试**失败（不是「随便红一下」）
- **② 3 例快照篡改** → 验证 INFO/WARN 的分类判据方向正确
- **③ 恢复后复验** → 确认破坏与恢复本身无副作用

安全边界：只在 `/tmp` 的**隔离沙箱**里改数据（从 `~/quant-data` 拷出的副本），
**绝不碰真实数据根**，结束时用 `-newer` 守卫复核。当前结果：

```
结构破坏  11/11 被抓到 ｜ 快照判据  3/3 符合预期 ｜ 恢复后 全绿
```

> 它**不参与**日常测试（会写 /tmp、耗时约 30 秒），只在**改动测试套件本身**或**怀疑套件失效**时跑。

## 目录

| 文件 | 作用 |
|---|---|
| `run_tests.py` | 统一入口（两层一起跑，只有第 ① 层影响退出码） |
| `test_invariants.py` | 结构不变量断言（unittest，可被 `python -m unittest discover -s tests` 发现） |
| `snapshot.py` | 数值快照采集 / 对比 / `--update` |
| `_common.py` | 期望 schema、值域约束、合法类别、加载器 —— **改口径时改这里** |
| `selftest.py` | 敏感性自测（注入破坏验证套件有效） |
| `baseline_snapshot.json` | 数值快照基线（**提交进仓库**，作为对比锚点） |

**改动清单（改了生产产物口径时）**：`_common.py:EXPECTED_COLUMNS`（列变了）→
`RANGE_CONSTRAINTS` / `REGIME_VALID_LABELS` / `LEDGER_VALID_SOURCES`（约束变了）→
`snapshot.py --update`（数值锚点）→ 连同 change doc 一起提交。
